# PROMPT 3 — Fix Railway & Vercel deploy failure (stale build cache after lockfile change)

## CONTEXT — read this first, the diagnosis is already done

Railway deploys are crashing at container start with:

```
Error: Cannot find package '/app/node_modules/multer/index.js' imported from /app/server.js
code: 'ERR_MODULE_NOT_FOUND'
```

Root cause (already verified): a recent `npm audit fix` changed `package-lock.json` (multer 2.1.1 → 2.2.0). The CODE IS FINE — a clean `npm ci` + `node server.js` boot and `npm run build` have been verified to succeed with the current repo state. The failure is a stale/corrupted `node_modules` build cache on the deploy platforms after the lockfile changed. Railway currently installs with plain `npm install` (see `nixpacks.toml`), which reuses the cached layer.

Your job: make the repo's build config deterministic, bust the Railway cache via a config change, push, and verify. Do NOT go hunting for bugs in application code — there are none related to this error.

## TASK 2 — Make the Railway install deterministic (this also busts its cache)

Edit `nixpacks.toml`:

```toml
[phases.install]
cmds = ["npm ci"]
```

(Only that line changes — leave `[phases.build]` and `[start]` as they are.)

Why: `npm ci` deletes any leftover `node_modules` and installs exactly what the lockfile says, so a cache can never leave a half-updated package behind again. Changing the build config also invalidates Railway's existing build cache on the next deploy — that is intentional and is part of the fix.

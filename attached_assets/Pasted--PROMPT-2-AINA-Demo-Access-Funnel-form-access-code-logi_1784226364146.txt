# PROMPT 2 — AINA Demo Access Funnel (form → access code → login), controlled by ONE admin-panel toggle

You are working on the AINA repo (Express monolith `server.js` + React/Vite frontend in `src/`, Supabase auth + DB, frontend on Vercel, backend on Railway). AINA has not launched publicly. For the demo/showcase phase, users must fill in a short registration form (personal data + a mini survey) and receive an ACCESS CODE, which they then use together with their email to log in.

The entire demo mode is switched on/off by a SINGLE runtime toggle: the `demo_mode` key in the existing `app_config` table, controlled from the admin panel. No env vars, no redeploys.

## CORE PRINCIPLE — everything must be ADDITIVE and TOGGLE-GATED

When it is `"false"` or missing, AINA must behave EXACTLY as it does today: the login page renders identically, `/akses-demo` redirects to `/login`, and the new endpoint returns 404. Fail closed: if the config cannot be read, treat demo mode as OFF.
- Do NOT touch the chat pipeline, anything in `engine/`, existing RLS policies, payment code, or CORS config.
- Do NOT delete or modify the Google OAuth login logic — only hide it when demo mode is on.
- Existing files you may edit, and ONLY in the ways specified: `src/pages/Login.tsx` (toggle-gated changes, Task 5), the routing file where pages are registered (add one route), the admin panel component that already renders `app_config` toggles (add one toggle, Task 6), and `server.js` — where you may ONLY (a) append new code, (b) add `"demo_mode"` to the whitelist array inside the existing `/api/app/public-config` handler (around line 14139, the `.in("key", [...])` list, plus its default in the `out` object), and (c) add one seed line `INSERT INTO public.app_config (key, value) VALUES ('demo_mode', 'false') ON CONFLICT (key) DO NOTHING;` next to the existing seed statements (around line 14939). No other modification to any existing handler.

## HOW IT WORKS (overview)

1. Admin flips the "Demo Mode" toggle in the admin panel → PATCH to the EXISTING `/api/admin/app-config` endpoint sets `demo_mode`.
2. Frontend reads `demo_mode` at runtime from the EXISTING `/api/app/public-config` endpoint (it has a 60s cache — that propagation delay is acceptable).
3. When ON: user opens `/akses-demo`, fills the form, frontend POSTs to `/api/demo/request-access`. Backend (service role) creates a real Supabase auth user — email = the user's email, password = a generated access code, `email_confirm: true` — stores the survey answers in a new table, prefills the user's AINA profile, and returns the code, which is shown on screen with a copy button.
4. On the login page (demo mode ON), the user enters email + access code → existing `signInWithPassword` → dashboard.

The access code IS the account password. No new auth mechanism.

## TASK 3 — Backend endpoint (append to `server.js`)

`POST /api/demo/request-access`:

1. First step: read `app_config` for key `demo_mode` (same `.single()` pattern used for `subscription_visible`, e.g. ~line 13947). If the value is not `"true"` — including on any read error — return 404 `{ error: "Not found" }`. Fail closed.
2. Rate limit: create a dedicated limiter with the existing `rl()` helper — 5 requests per hour per IP — attached to this route only.
3. Validate body: `full_name` (non-empty, max 100 chars), `email` (valid format, normalize to lowercase), `ai_importance` (integer 1–5), `study_field` (non-empty, max 100 chars). `origin_city`, `faculty`, `ai_importance_reason` optional (max 500 chars for the reason). Reject invalid input with 400 and an Indonesian error message.
4. Idempotency: if the email already exists in `demo_access_requests`, return the SAME stored `access_code` with `{ access_code, already_registered: true }` — do NOT create a duplicate user. This lets people who lost their code just re-submit the form.
5. Otherwise generate an access code `AINA-XXXXXX` where `XXXXXX` is 6 random chars from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (ambiguous 0/O/1/I excluded). Use `crypto.randomInt`, not `Math.random`.
6. Create the auth user with the existing admin client: `supabase.auth.admin.createUser({ email, password: accessCode, email_confirm: true, user_metadata: { full_name } })`. If Supabase reports the email is already registered as an auth user, return 409 with a friendly Indonesian message telling them to contact the AINA team.
7. The existing `handle_new_user` trigger auto-creates a `profiles` row. After creating the user, UPDATE that profile row (by `user_id`) with `full_name`, `origin_city`, `faculty`, `study_field` from the form so their AINA profile is prefilled.
8. Insert the row into `demo_access_requests` (including `access_code` and `user_id`).
9. Return 200 `{ access_code }`. Log errors with a `[DEMO-ACCESS]` prefix; never leak internal error details to the client.

Also append `GET /api/admin/demo-access-requests` (protected with the existing `verifyAdminUser` pattern) returning all rows ordered by `created_at` desc — so the admin can see survey results and help anyone who lost their code.
